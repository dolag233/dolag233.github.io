如何让AI成为“万能许愿机” —— AI时代的软件开发实践

在过去的一个半月里，我怒烧了 100 多亿 Token，产出了二十万行代码，最终开发出了一个具有较高完成度的跨平台资产管理软件Serpent。

在整个开发过程中，我只负责提出需求，没有编写哪怕一行代码，全部 20 万行核心代码与 10 万行测试代码，均由 AI 模型协同产出。这不得不说是一种“许愿式”的开发模式。

在技术社区里，“许愿式开发”常被用来调侃某些开发者向 AI 提出不切实际的要求、祈祷奇迹发生。但在我看来，今天的 AI 确实具备了某种“许愿机”的特质——前提是开发者自己要清楚想要实现的具体内容和实现思路，让“许愿机”按照你的想法实现愿望。

本文会基于Serpent项目的开发经验，详细介绍如何通过“软件工程”的缰绳让AI成为“万能许愿机”。

一、 立项：项目是否值得开发

软件工程的第一步永远是立项。在立项阶段，我们需要深入剖析竞品现状、锚定不可替代的核心价值，并充分评估开发落地的技术风险与不确定性，在动手前把缺口找准、把边界划清。

这个项目的出发点很简单。当时我在做自媒体工作，需要管理大量的视频、图片、参考素材与文案。但在网络上检索了一圈之后，发现现有的软件要么缺少专业格式支持，要么非得把文件复制一份存进库里占用双倍空间；更重要的是，基本没有高完成度的、方便二次开发的开源软件。于是就产生了自己动手做一个的想法。

放在过去，业余时间独自开发跨平台的中型桌面软件几乎不现实。但在代码生成成本趋近于零之后，这件事变得可行——前提是后续的软件工程能跟上。本文会着重分享我在 AI 开发过程中，关于软件工程的一线经验。

二、 需求：描述与对齐

在 AI 敲下第一行代码之前，最大的问题其实在于需求的描述。

如果把一句空洞洞的描述丢给 Agent，AI 会按照自己的想法随意发挥，最后生成一堆看似能跑、实则货不对板的玩具代码。

这正是由于需求描述不清导致的问题——试想假如世上真有万能许愿机，你使用语言描述的任何愿望都能够实现，那么你首先必须能够极其精确地描述你的愿望。为了制作你理想中的软件，你必须精确描述软件的所有行为：比如说这里有一个按钮，点击之后会怎样怎样；那边有一个文本框，输入之后会哪样哪样……需求的精准描述，是打造理想软件至关重要的一步。

当然，在进行顶层设计时，我们首先需要的是大方向的需求描述。为了厘清整个软件的方向，我借助了当时最强的前沿模型（如 GPT 5.6 Sol），并配合 grill-me skill，开展了一场长达数个小时的漫长澄清过程。

什么是 Grilling？就是让大模型扮演极其刁钻严苛的系统分析师与产品架构师，顺着系统设计的每一条分支不断向开发者提问。

在长达 100 多个问题的“轮番轰炸”之后，我脑海中原本模糊的想法被逐一厘清，拆解为具象的设计决策，最终整理成项目的核心需求文档——《产品简报》与《领域模型》。

软件工程的本质，就是把不确定的模糊想法逐步收敛成确定性的软件功能。有了明确精准的需求描述，AI 这台“许愿机”才能真正如你所愿。

另外，在实际操作中还需要注意两点：

  1. 需求对齐是动态持续的过程：软件开发是演进的，需求会随时发生变化。后续开发如果涉及到较大的功能或逻辑调整，最好都和大模型重新做一遍需求对齐，更新文档，绝不能脑子一热就让 Agent 盲目修改代码。
  2. 需求描述的载体不限于文字：虽然绝大多数业务逻辑依赖文字定义，但对于界面排版、视觉层级与微交互，一张参考截图、草图甚至竞品软件的截图，往往比写上千字描述都更加精确高效。

三、 拆解：架构分层与任务拆解

需求对齐之后，下一个问题随之而来：面对一个庞大而复杂的系统，如何将其拆解为清晰的架构与可执行的任务？

坦白讲，作为一个没有大型软件开发经验的独立开发者，我自身并不具备完备的架构设计能力。但在如今大模型的加持下，这不再是个硬门槛——既然前一步已经梳理出了详细的需求文档，我就可以直接把它喂给能力较强的大模型，让它帮我一起推演，自顶向下完成系统的模块拆解与架构分层。

1. 软件架构

大模型帮 Serpent 梳理出的架构非常清晰，主要分为以下几个核心模块：

  • 界面层（Renderer）：纯前端 React 界面，负责 UI 展示与用户交互。它处于沙箱环境中，不能直接读写文件或数据库，哪怕前端报错崩溃，也不会影响底层数据；
  • 后台核心服务（Library Worker）：一个独立的后台服务进程，作为数据库与文件 I/O 的唯一持有者，专门负责处理资产扫描、文件导入、元数据解析和缩略图生成等重型计算，绝不卡死前台界面；
  • 主进程与桥接（Main & Preload）：负责桌面窗口管理、系统菜单以及安全的进程间通信。

有了这套模块划分，就等于给 AI 写代码划定了清晰的职责边界，避免后续开发时把界面逻辑和底层数据搅合在一起。

2. 任务拆解

有了顶层架构之后，任务拆解其实就顺理成章了。

我们同样可以直接把需求交给 AI，将其逐步拆解成极小的、独立的、并且可测试和可验收的小目标。

比如做资源管理，不需要让 AI 一上来就做一整套复杂的系统，而是切分成具体的小步骤：先做“能够新建和打开空资源库”，跑通验证；再做“把一张图片导入并存进数据库”；接着再做“列表展示和缩略图生成”。

这样拆解出来的任务，功能范围小、代码改动少、目标明确。一方面 AI 极不容易跑偏，另一方面也非常适合使用一些便宜模型进行快速开发，实乃性价比之选。

四、 编码：组织 Agent 干活的现实考量

任务和架构拆好之后，接下来就是怎么具体拉 Agent 进场写代码。在实际组织 Agent 编写代码与工程交付时，有几个非常实在的经验：

1. 把开发日志当作交接班日记

每个开发 Agent 会话结束时上下文都是“阅后即焚”的，而单纯的代码只能反映最终写成了什么，无法看出之前踩过哪些坑、试过哪些行不通的废弃方案，以及用什么命令验证了现场。为了避免下一个进场的 Agent 在同一个坑里反复跌倒甚至把死路重走一遍，我们要求必须像交接班日记一样，把开发日志实时写入仓库：记清楚干了什么、踩了什么坑、跑了什么命令验证，以及留下了什么隐患。新 Agent 进场扫一眼日志即可避开所有弯路，真正做到无缝接棒。

2. 高覆盖率测试：2:1 的代码比

在代码交付上，Serpent 的功能源码与测试代码比例约为 2:1（18.6 万行源码对应 10.6 万行测试），维持了极高的自动化测试覆盖率。

我们每次让 Agent 写完功能，必须同步编写对应的单元测试和集成测试。当然，测试覆盖率只能保证基础功能的逻辑可用，但在真实复杂环境下的可用性依然是个未知数，具体的人工 QA 验收过程我会在后文展开说明。

3. 关于并行开发

在一些纯后端的项目可能可以使用高并行度的开发，但在我们项目的实际开发中，并没有进行大规模并行开发，原因很无奈：

首先是代码隔离问题。并行开发如果要完全隔离环境，往往要借助 Git Worktree 创建多个工程副本，这样的使用太过重度，搞得我洁癖犯了 其次是成本问题。并发跑十几个Agent，每个会话都要维护独立的上下文，Token 成本急剧飙升，作为自掏腰包的独立开发者，性价比非常关键。 最后是人类效率问题。代码生成几乎是零成本的，但人类点验和消化的精力是有限的。一旦并行铺开，未经验证的代码迅速堆积，反而容易变成负担。

因此，绝大多数时间保持节奏可控的单线推进，反而是成本最低、最踏实的选择。

五、 人类的核心价值：产品把控、真实验收与审美把控

在实际开发中，我的精力彻底从“写代码”中解放出来，转而投入到三件更关键、也是 AI 完全替代不了的事情上：产品构想与走向把控、真实验收，以及交互审美打磨。

1. 产品构想与走向把控

AI 永远只是被动的执行者，它不会凭空构想出一个产品，更不知道真实世界里的人到底需要什么。

整个产品的灵魂、所有的功能与业务逻辑，全部都是由开发者发起，决定这款软件的走向，决定软件的价值。这是人类在开发中最重要的作用。

2. 真实的 QA 验收

代码写完，绝对不代表软件就能用、好用。在软件工程里，QA正是保障软件真正稳定、可用、不崩溃的关键防线。

但是QA并不等同于自动化测试。熟悉Vibe Coding的同学都知道，“测试全绿”大概是 Agent 开发中最大的骗局。因为测试用例往往也是 AI 自己写的，它极其擅长“自产自销”：比如测试一个图片展示功能，它写的测试可能只检查界面上有没有留出放图片的位置；至于图片文件到底能不能正常解码渲染、会不会黑屏报错，它根本不管，直接判定通过。

哪怕当时使用了具备计算机控制能力的模型（如当时的 GPT 5.6），面对复杂的桌面软件依然力不从心——多窗口来回切换、拖拽时是否跟手、复杂的操作时序，AI 根本体会不到。因此只有极少数行为非常明确的小步骤能交给它看一眼。

为此，项目开发中我们维护了一套“人类验收清单”，所有可验收的内容都必须通过人类验收才能算通过。这就要求绝大多数可测试的功能，都必须由人类在真实的电脑环境下一项项去点、去试。不管自动化测试报告写得多漂亮，只要自己没在屏幕上亲自测试过，这个功能就绝不能算真正做完。

在开发后期，人类 QA 环节反而成为了整个项目的瓶颈，常常测得精疲力竭，只盼着未来的大模型能在测试验收上变得真正靠谱。

3. UI/UX 打磨与审美把控

AI 的前端能力也许被吹得天花乱坠，但它在审美与交互体验上存在明显短板，需要用规则进行限制。

为此我总结了一些比较实用的UI/UX原则，以下是其中比较重要的部分：

  • 样式统一与组件复用：AI 编写前端组件时，极其喜欢在各个局部随手新建样式类，或者将各种参数硬编码。结果就是各个界面风格脱节、各显神通，一旦切换深浅色主题界面直接崩溃。必须建立一套统一的颜色和样式规范，逼着它所有界面必须复用这套统一的设计系统。
  • 减少冗余信息：AI 毫无设计直觉与品味，倾向于过度装饰——动不动就创建过多冗余的UI。我们必须帮它做减法：对于一些一眼就能明白的内容，尽量用UI表达功能，而不是使用文字进行指示。 同时，能用icon明确表示的就不要添加文字描述，UI越简洁越好。 像这样的“简化”数不胜数，核心都在于减少“冗余”信息，同时还需保证用户使用体验。下图是一个典型的简化效果，使用简要的UI告诉用户使用方法，而不需要靠冗余的文字。
  • 降低不安感：AI总喜欢使用一些危言耸听的文字和样式，动不动就爱使用“严重错误”、“致命灾难”等词汇吓唬用户，实际上我们只需要在真正严重、危险的情况下才会选择使用“错误”进行警告，以避免引起用户的恐慌和不安。
  • 设计语言统一：项目的一大设计语言是将资产包装成“卡片”，因此我们的资产浏览、资产选中、资产预览全都是以卡片的形式呈现，甚至鼠标移动到资产预览图上还会有卡片交互动效，整体观感比较统一。

事实上AI很难完全遵循这些原则，因此开发过程中我们仍然花费了巨量的时间进行细节的打磨。

六、 项目管理：给“许愿机”搭好脚手架

即便是单人开发中大型软件，也同样需要建立一套项目管理机制，否则面对庞杂的代码与任务，开发过程很快就会陷入一团乱麻。

1. 纯文本的工单系统

工单系统是工程开发中的“神经中枢”，它将复杂的开发目标拆解为可追踪、带状态的工单，确保在任何时刻都能知晓项目的当前状态、待办。

传统的外部项目管理工具并不是AI原生的工具，使用起来不免有些笨重。最初用过一套名为 Beads 的命令行工单工具，但它底层依赖二进制数据库，还依赖github hook，重度且难用。反复踩坑之后，我们彻底换成了最朴素的方案：基于纯文本单行 JSONL 的工单系统。

每一条任务就是文件里的一行 JSON 数据，直接跟随 Git 版本流转。Git 本身最擅长的就是存文本，分支随便切，毫无同步包袱与数据库冲突；再配合一个极简的命令行脚本，Agent 在终端敲一行命令就能查任务、领工单。对大模型来说，命令行和纯文本就是它最天然、最高效的工作环境。

2. 工作留痕，维护项目知识库

在实际开发中，我们维护了完整的项目知识库：任何需求讨论、架构决策、功能开发和用户反馈，都必须写成文档存进 Git 仓库，做好工作留痕。

这种工作留痕在多数时候都没有太多作用，但在关键时刻却至关重要，所谓养兵千日，用兵一时：

  • 明确决策原因：不管是人还是 AI，回看代码时最痛苦的往往不是看不懂代码，而是想不通“当初为什么要这么设计”。把技术选型和设计取舍记录下来，以后维护时才清楚为什么选了这个方案而不是另一个，才不会误把当初深思熟虑的妥协当成 Bug 盲目修改；
  • 排查疑难 Bug 与追溯上下文：当系统出现异常或离奇报错时，翻看当时的修改记录和排查思路，能迅速理清前因后果，立刻定位到引入问题的现场；
  • 形成项目的知识库与复盘档案：把踩过的深坑和成熟解法记录在案，后续无论是自己复盘重构，还是开发新模块，都是随时可查的宝贵经验。

七、 结语：从“代码自由”迈向“软件自由”

AI 确实是一台令人惊叹的“万能许愿机”，它将原本昂贵的代码变成了可流水线式产出的产品，带来了前所未有的“代码自由”。

但必须注意是：代码自由!=软件自由。

能把愿望真正变成现实的，从来不是许愿机本身，而是许愿的那个人到底知不知道自己想要什么，以及有没有能力给许愿机套上缰绳、立好规矩、把控方向。
